# SCQ16 (byte-granular packet encoding with an MD32-like scalar model) — notes for the `scq16` CPU mode

Hand-over notes for the `scq16` cpu of the md32 plugin: the encoding model the decoder implements, the table that drives it, the
analysis and ESIL conventions, and what is not modelled.  See README.md "SCQ16 mode" for the user-facing description.

Relation to MD32: the SCQ16 instruction encoding is not an MD32 encoding (neither MS15E30 nor the uSIP VLIW variant): its
length rule, opcode space and vector operations are its own.  What it shares with MD32 is the scalar programming model (32
general registers, `sp`/`lr` as control registers, the calling convention, the scalar operation set and therefore the ESIL),
which is why it is served as a cpu mode of this plugin rather than as a separate architecture.  The other DSP cores of the
same modem (an unrelated SIMD ISA) are out of scope.

## 1. Encoding model

The SCQ16 is a byte-granular, big-endian instruction stream.  The minimum unit is the byte; an INSTRUCTION is one of:

* a **stand-alone unit** of 2, 3, 4, 5 or 6 bytes (the length is decided by the first byte and, for some first bytes, a prefix of
  the second: the "length leaves" `scq16_uleaves` of `scq16_opcodes.h`);
* a **packet** `{ A ‖ B }`: a head unit whose first byte has bit 7 set (`80-bf`, or `e0-ef` for a vector head) followed by a second
  unit B.  The head is decoded as A' = (unit << 1) | bit7(B): every byte shifted left by one with the top bit of the first byte of B
  borrowed into the last bit.  The length of the head is the length of A' (leaves `scq16_hleaves`).  B is decoded with its bit 7
  masked (`b0 & 0x7f`; a raw `c0-df` first byte is a 4-byte vector op).  The two units execute in parallel: both read the
  pre-packet state.  Control flow is never a head; a B that is a transfer takes the packet start as the base of its displacement.
  A head whose A' would be a control/system form is not a packet but a **masked orphan**: the unit decoded with `b0 & 0x7f` on its
  own (`.p` suffix).  `f8-ff` first bytes are orphans too;
* a **vector operation** of 4 bytes with first byte `c0-df` (`110 A B F1 F2 F3 op9`: a 3-bit A, a 2-bit B, three 5-bit register
  fields and a 9-bit op9 code);
* a **bundle** of 8 bytes with first byte `f0-f7`: `{11 | vec32 | s1 | s2}`, a 32-bit vector operation and two 15-bit scalar slots
  decoded as 2-byte units.

Delay slots: `.d1` / `.d2` / `.d3` mnemonic suffixes mean one, two or three INSTRUCTIONS (packets included) executed after the
transfer; `do` (hardware loop setup) also has `.d1`/`.d2` variants, and the loop body starts after the slots.

One length is decided by the target: a first byte `56` with the top two bits of the second byte clear is the 4-byte `j.d1` when
its 22-bit displacement (from the packet start in a B slot) lands on a plausible code address (no wrap below 0, below 4 MB), and
a formless 2-byte unit otherwise (the 2-byte reading has no form; a function table, which the plugin lacks, would decide by membership).

## 2. The table

`scq16_opcodes.h` is generated by `tools/gen_scq16_tables.py` from `isa/scq16_isa.json`, the ISA table (forms, bit
alternatives, operands, text and ESIL templates, the length-rule leaves, the vector classes and the register names; `make
scq16_opcodes.h` regenerates the header, and `tools/gen_scq16_tables.py export` builds the JSON from a Python module that
describes the forms and from the length-rule leaves): one
`Scq16Alt` per bit alternative with `(w & mask) == value` on the
transformed unit (w = big-endian integer of the unit, bit 0 = LSB of the last byte; bit 7 of byte 0 is never in a mask, so the
same entry serves a stand-alone unit, a head A' and a B slot), the operands (`Scq16Operand`: register fields r0-r31 / r0-r15 /
r1-r16 / r1-r8, csr, acc, immediates with up to two pieces, scale and bias, displacements, constants), the text template, the
ESIL template, the delay-slot count and flags (`SCQ16_FL_NAMED`: an established operation name; `SCQ16_FL_PROV`: provisional name
with `?`; `SCQ16_FL_TABLELEN`: a form tied to the length table; `SCQ16_FL_CONTROL`: never a packet head; `SCQ16_FL_HYP`: the ESIL
is a hypothesis).  Within one length the first matching alternative wins (the table is ordered by specificity).  The vector
classes (`scq16_vclass[512]`) and names (`scq16_vname[512]`) are indexed by op9; a name carries its `?` when it is provisional
(`movi?`, `add?`, `addi?`, `adds?`, `difsc?`) and none when it is an established operation (`v.move.mv` = register copy v[F1] <- v[F3],
`v.mem.ld` = vector load into v[F1 >> 2], `v.mem.st` = vector store of v0): the decoder prints `v.<class>.<name>` as the table says.

## 3. Analysis

`scq16_decode_r2()` (scq16_arch.inc.c) decodes one instruction and fills the RAnalOp: the type from the unit that carries the
control flow (the B slot of a packet, the s2 slot of a bundle, the unit itself), `jump` from the table displacement (base = packet
start), `fail` = the address after the delay slots (decoded ahead from the bytes at hand; MAXOP_SIZE is 12 so that the analysis
sees a 6+6 packet and the slots), `delay` = the slot count, `cond`/`sign` for branches, `reg` for register jumps/calls/returns,
`ptr` + `direction REF` + `reg`/`val` for `do`, `refptr`/`ireg`/`disp`/`stackop` for memory and stack forms, `val` for immediate
moves.  A packet without control flow has type `unk` (two operations cannot be summarised by one scalar type): its two operations
are in `opex.units[]`.

## 4. ESIL

* A unit's ESIL is its table template with the operands substituted (`{op}` read, `{=op}` write, `{#op}` decimal value for
  register names, `{d}` target, `{ret}` return address after the slots, `{mask}` of a bit-field width).  A packet is A then B
  with the registers that B reads and A writes copied to `t0-t3` first (parallel semantics).  An instruction with a unit without
  semantics (vector classes without `vop`, placeholders) has no ESIL.
* Delayed transfers: `target,SETJT,n,SETD` (n = slots); `aes` executes the slot and then applies the jump.  Conditional branches
  wrap it in `?{ }`.  A `.d2` transfer takes two `aes` steps: the first runs the transfer and its first slot (a packet counts as
  one instruction), the second runs the second slot and applies the jump.
* Memory addresses: the ESIL machine computes in 64 bits and `aes` does not mask addresses, so every `[n]` / `=[n]` access
  cuts its address to 32 bits (`0xffffffff,&`): negative frame offsets (`lw.sp r1, -0xfc(sp)`) reach the 32-bit frame.
* A unit whose ESIL is the empty string (no modelled effect: `nop`, `halt`, `ieon`/`ieoff`, `loopend`, `vwait?`, `sys41`)
  does not block the ESIL of its packet.
* Memory order inside a packet: the ESIL runs A before B with B's register reads taken from the pre-packet values; a B load
  therefore reads the memory AFTER a store of A, and a B store after a load of A (the hardware order between the two memory
  accesses of one packet is not established).  The two slots of a bundle run in order s1, s2 after the vector operation.
* Comparisons: `<`/`<=` read 32-bit registers with sign, so unsigned compares normalise both operands with `,0,+` and signed ones
  extend with `32,x,~`; `div` writes `a0l` (quotient) and `a0h` (remainder), `~/`/`~%` for the signed variant.
* `do` writes `lc0`/`le0`/`ls0` (count, end, body start); the back edge is not applied by the ESIL (an emulator must do it).
* A load with a post-increment writes its destination LAST (load, increment the base, write rd): with `rd == rb` the loaded value
  wins.  This is a declared convention (no such unit is known); the public MD32 documents rd written first.
* The VU scalar ports are registers (`vu0-vu31`, `v0-v31`, `va0-va7`, `vp0-vp7`, `vs0-vs15`, `vb1_0-31`, `vb3_0-31`, `vb5_0-31`,
  `udf0-udf31`); a vector operation is `F3,F2,F1,B,A,op9,vop` with the custom op `vop` registered by `esilcb`.  The VU model
  (`scq16_vu.inc.c`): a vector register file `vr0-vr31` of 128 bytes each (64 lanes of 16 bits; exposed as four 256-bit quarters
  `vrK_0..vrK_3`, lane 16q being the low 16 bits of quarter q), the pointers `vp0-vp7` (written by `vmem.set` and the hypothetical
  `vcfg4c? #0xc`) and the counts `va0-va7` (written by `vset.a`).  `vop` models the three established operations and nothing else:
  `v.mem.ld` copies `n` halves from DM[p] into `vr[F1 >> 2]` and `v.mem.st` copies `n` halves from `vr0` to DM[p], with
  `p = vp[2 * F2 + F3[4]]` when `F2 < 4`, `n = va[A]` when 1..64 (otherwise the whole register: the count field of a large packed A is
  not established) and the pointer post-incremented by the bytes accessed; `v.move.mv` copies `vr[F3]` into `vr[F1]`.  A memory op
  with `F2 >= 4` (the second access family, whose pointer is not established), the pair mode `B = 2` of `v.move.mv` and every other
  op9 have no effect.
* `SCQ16_FL_HYP` alternatives (`cmov.leu?`/`ltu?`/`lt?`/`le?`, `lhu.post?`, `ld46?`/`lhu?` of `46`, `lbu?`/`lh?` on the stack,
  `sys41`, `vbcast.i?`, `vcfg4c?` `#0xc`, the VU bank ports) carry the ESIL of their provisional reading; an emulator that wants
  to be strict can refuse them.  The HYP table of the form-description module is exported as the flag: the exporter applies no overlay of its own.

Register profile: `r0-r31`, `pc`, `sr`, `ipc`, `isr`, `csr3`, `lf`, `ls0-2`/`le0-2`/`lc0-2`, `sp` (csr14), `lr` (csr15),
`csr16-31`, `a0` (`a0l`:`a0h`), `t0-t3` (ESIL temporaries), the VU ports, `vr0_0-vr31_3` (the vector register file).  ABI: arguments
r3-r6, return r1; callee-saved r16-r31 (a function that writes one of them saves and restores it on its frame), caller-saved
r0-r15 (frame stores of r1-r8 are spills), lr saved by the functions that call.

## 5. Limitations

* The vector unit is modelled only for `v.move.mv`, `v.mem.ld` and `v.mem.st` (section 4): the lane arithmetic of the other op9
  codes, the pointer of the second access family (`F2 >= 4`), the count field of a large packed A, the pair mode `B = 2` of `v.move.mv`
  and the role of `F1 != 0` / `B = 1` in the stores are not modelled (`vop` has no effect there).  No semantics for the
  `op41`/`op41.fld`/`op43`/`op67`/`op6f`/`op4x`/`op6x` placeholders, `vcfg4c?` except `#0xc`, `vpmem?`, `sys`, the `74` sub-op 3, the six
  `sel?` codes without a name, the provisional masks `and? #0xf000?`/`#0xfc00?`/`#0xc000?`; `fup` with overlapping fields is a plain insert.
* The length of `j.d1 56 0x-3x` is decided by the target (section 1) because the plugin has no function table to decide by
  membership: a `j.d1` whose target is outside the loaded code would still be read as `j.d1`.
* The plugin annotates no DM strings nor I/O registers; the I/O window (`ior`/`iow`) is modelled as memory at the port index.
  The data-space bases of the SCQ16 are available as flags (`tools/scq16_flags.r2`: `scq16.dm_main` at 0, the I/O window at
  0x8000, `scq16.dm2` at 0x40000); the data memory is little-endian, the instruction stream big-endian.
* Confidence levels live in the ISA table, not in the plugin; provisional names keep their `?`.
