# MN10300 / AM33: encoding model and plugin decisions

## Instruction stream

The MN10300 instruction stream is byte-granular. The first byte decides the
length (1 to 7 bytes) through the prefix rule of `opcodes/m10300-dis.c`
(`mn103_insn_size`): the one-byte register forms `0x00`-`0x7f`, `0xcb` (`nop`),
`0xd0`-`0xdb` (the loop forms), `0xe0`-`0xef`, `0xff` (`break`); the two-byte
forms `0x80`-`0xbf` (unless the two register fields are equal, which marks the
one-byte register-to-register move), `0xc0`-`0xca` (branches), `0xf0`-`0xf6`
(the `F0`-`F6` extension pages); three bytes for `0xf8`/`0xf9`, `0xcc`, `0xde`,
`0xdf` and the 16-bit absolute moves; four bytes for `0xfa`/`0xfb` and the AM33
`0xf7` pair page; five for `0xcd`/`0xdc`; six for `0xfc`/`0xfd`; seven for
`0xfe` (five for `FE 8x`) and `0xdd`.

Within a length, the table rows are tried in order and the first row whose
`(mask & insn) == opcode` holds and whose machine level is accepted wins. The
operand fields are then read from the opcode word and, for the wider
formats, from the little-endian "extension" bytes that follow it, exactly as
binutils does (the `SPLIT`, `24BIT`, `EXTENDED` and FPU register field rules
are ported verbatim). This is why the output can be checked against `objdump`
row by row.

Unknown encodings are reported as `invalid` with size 1 so that a linear sweep
resynchronises at the next byte; `tools/mn103-dis` keeps the binutils
behaviour (consume the length-rule size) because it exists to be compared with
`objdump` output.

## Machine levels

The table tags each row with the machine that introduced it: base MN103 (359
rows), AM30 (15), AM33 (611) and AM33-2 (144, the FPU). binutils accepts a row
only for an exact `-M` match (`-M am33` does not accept the AM30 rows); the
plugin accepts the chain `mn10300 < am30 < am33 < am33-2`, which is how the
cores are documented (every AM33 implements the AM30 extensions).

The `udf00`-`udf15` / `udfu00`-`udfu15` rows are placeholders for the
*user-definable function* slots (`F6 Nx` register forms, `F9 Nx` / `FB Nx` /
`FD Nx` immediate forms). The AM30 and AM33 rows give names to some of them
(`mulq` = `udf00`, `mulqu` = `udf01`, `sat16`/`sat24` = `udf04`/`udf05`,
`mcst9` = `udf03`, `mcst48` = `udf06`, `bsch` = `udf07`, `swap` = `udf08`,
`getchx`/`getclx` = `udf12`/`udf13`, `getx` = `udf15`) but the placeholder rows
come first in the binutils table, so `objdump` prints the slot number unless
the machine is set to AM30. The generator moves the placeholder rows after the
named rows; the lookup therefore prefers the name whenever the cpu level
accepts it. Nothing else in the table is reordered.

The AM33-2 FPU rows overlap most of the `F9`/`FB` `udf` immediate slots (slots
2-7 and 10-15 on `F9`, 2-15 on `FB`); those remain FPU instructions, as in
binutils, since the FPU rows precede the placeholders.

## Operands

The row's operand list is reduced to logical operands: register, immediate,
memory (base, optional index register, displacement or absolute address,
post-increment with the access size or the explicit amount), PC-relative
target, register list. The source comes first and the destination last, which
the analysis and the ESIL rely on (`mov d0, (0x8, a2)` is a store; `add 0x4,
sp` adds to `sp`). The AM33 three-operand forms (`add rm, rn, rd`) put the
destination last as well.

Register names follow binutils: `d0`-`d3`, `a0`-`a3`, `sp` when the row names
the stack pointer explicitly (`a3` and `sp` are the same register and share the
offset in the register profile), `r0`-`r7` for the AM33 extended registers
(`r8`-`r15` in the 4-bit field are `a0`-`a3`, `d0`-`d3`), `xr1`-`xr15` (`xr0`
is `sp`), `fs0`-`fs31` / `fd0`-`fd30`, `psw`, `epsw`, `mdr`, `usp`, `ssp`,
`msp`, `pc`, `fpcr`.

## Stack and calls

`call label, [regs], imm8` saves the return address in `mdr` and on the stack,
pushes the register list, then subtracts `imm8` (the callee's frame).
`ret [regs], imm8` undoes it from the stack; `retf` restores the registers and
returns through `mdr` (the fast path a compiler uses when `mdr` survived). The
stack delta reported to the analysis is therefore `4 + 4 * |regs| + imm8` on
the call and its negative on the return. `calls` / `rets` are the plain
push/pop pair.

The `movm` register-list layout follows `arch/mn10300/include/uapi/asm/ptrace.h`
of Linux 4.16 (`pt_regs` is built with two `movm` pushes): from the lowest
address, `a3`, `a2`, `d3`, `d2`, then `exother` (`mcvf`, `mcrl`, `mcrh`,
`mdrq`), `exreg0` (`e1`, `e0`), `exreg1` (`e7`..`e2`), and `other` (the dummy
word that Linux uses for `usp`, `lar`, `lir`, `mdr`, `a1`, `a0`, `d1`, `d0`).
The relative order of `other` with the extended groups in a single `movm` is
not observable in Linux (it pushes `other` separately); the plugin places it
highest. The extended registers `e0`-`e7` are the AM33 `r0`-`r7`.

## Flags

PSW bits 0-3 are Z, N, C, V (`zf`, `nf`, `cf`, `vf` in the profile). The ESIL
sets Z and N on every arithmetic, logic and shift result, C and V on `add`,
`addc`, `sub`, `subc` and `cmp` (C is the borrow on subtract, as on the MN10300),
clears C and V on the logic forms, and leaves C untouched on the shifts (the
hardware moves the last bit out into C; not modelled). `btst`, `bset` and
`bclr` set Z from the test and N from the top bit of the tested value.

The branch conditions use the manual's definitions: `bgt` = !(Z | (N ^ V)),
`bge` = !(N ^ V), `ble` = Z | (N ^ V), `blt` = N ^ V, `bhi` = !(C | Z),
`bcc` = !C, `bls` = C | Z, `bcs` = C, `bvc`/`bvs` on V, `bnc`/`bns` on N.

## Loops

`setlb` saves the address of the following instruction in `lar` (and its
first four bytes in `lir`, the hardware's loop-instruction cache); the `lXX`
forms jump to `lar` when their condition holds. The plugin types them as a
conditional jump through `lar` with the fall-through as `fail`; the target is
only known once `setlb` has executed, so it is not reported statically.

## What was checked

The decoder was compared with a Python port of `m10300-dis.c` on the AM33
firmware of three Olympus / OM System cameras (the code regions of the main
µITRON module, 2.05 M instructions, plus the 512 KB boot block): identical
mnemonic and length everywhere except the named `udf` slots and the truncated
last instruction of each region. The ESIL was checked by emulation of the
forms the firmware uses most (`mulq`/`ext`/`div` sequences, compares and
branches, `call`/`ret` frames, `movm`, stack-relative moves, absolute memory
and bit operations, `setlb`/`lne` loops). `aaa` on the boot block (512 KB,
1830 functions) runs in about 1.5 s.
